# devices-api

A REST API for managing devices (name, brand, state), backed by PostgreSQL,
with state changes streamed to subscribed clients over Server-Sent Events.

## Run

Requires Docker. To run or test outside containers, you also need Go 1.27.4.

```sh
make run              # build and start the API and Postgres on http://localhost:8080
make down             # stop everything (data is kept in a volume)
```

API documentation: **http://localhost:8080/docs** (Swagger UI; you can send requests from it).
The raw OpenAPI spec is at `/openapi.yml`.

## Test

```sh
make test-container   # all tests, including Postgres integration tests, in Docker
make test             # unit tests with local Go; Postgres integration tests are skipped
make psql             # open psql on the running database
```

`make test-container` uses a separate, in-memory test database, so it never touches the data from `make run`.
Plain `go test ./...` skips the Postgres tests unless `TEST_DATABASE_URL` is set.

## API

| Method | Path | Description |
|---|---|---|
| `POST` | `/devices` | Create a device (`state` defaults to `inactive`) |
| `GET` | `/devices` | List devices; filter by `brand` or `state`, paginate with `cursor` and `limit` |
| `GET` | `/devices/{id}` | Get a device |
| `PATCH` | `/devices/{id}` | Update the fields sent (send every field for a full update) |
| `DELETE` | `/devices/{id}` | Delete a device |
| `GET` | `/devices/events` | Stream state changes (Server-Sent Events) |
| `GET` | `/healthz` | Liveness check |

Rules:
- `created_at` is set by the server and can never be changed.
- `name` and `brand` cannot change while a device is `in-use` (409).
- Devices that are `in-use` cannot be deleted (409).
- State changes are announced only after they are saved.

Errors are JSON: `{"error": "device not found"}`, with 400, 404, 409 or 500.

### Examples

```sh
# Create
curl -i -X POST localhost:8080/devices -d '{"name":"iPhone 15","brand":"Apple","state":"available"}'

# Get
curl localhost:8080/devices/<id>

# List: all, by brand (case-insensitive), by state, next page
curl localhost:8080/devices
curl 'localhost:8080/devices?brand=apple'
curl 'localhost:8080/devices?state=in-use'
curl 'localhost:8080/devices?limit=10&cursor=<next_cursor>'

# Update: partial
curl -X PATCH localhost:8080/devices/<id> -d '{"state":"in-use"}'

# Delete
curl -i -X DELETE localhost:8080/devices/<id>

# Watch state changes (in a second terminal, then PATCH a device's state)
curl -N localhost:8080/devices/events
# event: state-changed
# data: {"device_id":"…","previous_state":"available","new_state":"in-use"}
```

## Design

**Layout.** `handler → service → repository`, one package per concern under `internal/`:

| Package | Responsibility |
|---|---|
| `device` | Domain types, business rules (`Service`), HTTP handler and DTOs |
| `postgres` | Repository implementation, embedded migrations |
| `notify` | Event broker and the SSE endpoint |
| `docs` | OpenAPI spec and Swagger UI page |
| `health`, `router`, `config` | Liveness, route registration, environment config |

Interfaces are defined where they are used (the handler's `deviceService`, the service's
`Repository` and `Notifier`), so each layer is tested with small hand-written fakes.

**Data.**
- IDs are UUIDv7, generated by the service. They sort by creation time, so they double as the pagination key.
- `state` is a Postgres enum, so invalid values cannot be stored.
- Timestamps are set by the database (`created_at DEFAULT now()`, `updated_at = now()` on update).
- Deletes are soft (`deleted_at`). Deleted devices are excluded from every query.
- Migrations are embedded in the binary and applied with goose on startup.

**Listing.** Keyset pagination (`WHERE id > $cursor ORDER BY id LIMIT n`), so every page costs
the same and no `COUNT` query runs. The service asks for one extra row to know whether a next page
exists. Partial indexes on `(id)`, `(lower(brand), id)` and `(state, id)`, all `WHERE deleted_at IS NULL`,
match the three list queries.

**Concurrency.** Update and Delete lock the row with `SELECT … FOR UPDATE` inside a transaction,
so the "in use" checks see the current state and cannot race with another request. For updates,
the repository takes a function from the service: the business rules stay in the service and run
under the lock. Integration tests check that a concurrent change is waited for and seen.

**Updates.** `PATCH` changes only the fields sent; unknown fields (such as `created_at`) are rejected.
Sending every field is a full update, so there is no separate `PUT`.

**Notifications.** After an update commits, the service notifies if the state changed. The broker
sends to every subscriber without blocking the request; a subscriber that falls too far behind
misses events instead of slowing updates down. On shutdown the broker closes open streams.

## Approach

- **Standard library first.** `net/http` routing, `log/slog` and `encoding/json` from the standard
  library, plus a few well-known packages where they earn their place: pgx (Postgres),
  goose (migrations) and google/uuid.
- **Attention to detail.** Domain rules are enforced where they cannot be bypassed: row locks for
  concurrent updates and deletes, immutable `created_at`, rejected unknown fields, clean error
  messages, and graceful shutdown that also closes open event streams.
- **Small, explained steps.** The git history builds the service one layer at a time, so each
  decision can be traced to the commit that made it.
- **Tests that prove behaviour.** Every layer is tested: business rules with fakes, HTTP mapping
  with recorded requests, and the repository against a real Postgres, including race tests that
  fail if the row locks are removed.

## Next steps

- End-to-end tests that go from HTTP through the service to Postgres.
- Users and authentication, required on every endpoint.
- Permissions, so users only see and change the devices they are allowed to.
- Rate limiting.
- Subscriptions to specific devices or filtered sets, instead of every state change.
- Persist notification events (Postgres or a message broker), so clients can catch up on missed
  events and several API instances share the same stream.
- Secrets from a secret store, and a `.env` file for local settings.
- Configurable local ports.
- Staging and production environments, while keeping the local setup.
